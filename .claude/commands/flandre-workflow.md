# Flandre Workflow - 需求开发工作流

用户输入了需求相关的内容，并明确要求以"需求工作流"执行。请严格按照以下流程执行。

---

## 第零步：判断输入类型

- 如果用户给出的是**需求描述**（非正式需求文档），进入 **路径 A**
- 如果用户给出的是**需求文档**（完整的 PRD / 功能规格说明），进入 **路径 B**

---

## 路径 A：从需求描述生成需求文档

### A1. 头脑风暴

基于用户的需求描述，进行头脑风暴：

1. **需求拆解**：将描述拆解为独立的功能点
2. **用户故事**：为每个功能点编写用户故事（As a ... I want ... So that ...）
3. **边界场景**：列出可能的边界情况和异常场景
4. **优先级排序**：对功能点进行优先级排序（P0/P1/P2）
5. **技术可行性**：初步评估技术可行性，列出可能的技术选型

### A2. 生成需求文档

将头脑风暴结果整理为需求文档，使用 Markdown 格式，包含以下章节：

```markdown
# {需求名称} - 需求文档

## 1. 背景与目标
<!-- 为什么要做这个需求，要解决什么问题 -->

## 2. 功能概述
<!-- 一句话概括核心功能 -->

## 3. 功能详情

### 3.1 功能点 1
- **用户故事**：As a ... I want ... So that ...
- **详细描述**：...
- **验收标准**：
  - [ ] 标准 1
  - [ ] 标准 2

### 3.2 功能点 2
...

## 4. 边界与异常
<!-- 边界场景、异常处理 -->

## 5. 非功能需求
<!-- 性能、兼容性、安全性等 -->

## 6. 优先级
| 功能点 | 优先级 | 说明 |
|--------|--------|------|
| ...    | P0/P1/P2 | ... |
```

### A3. 创建文件夹并写入

1. 在 `E:\###project\prd\lolachievements\feat\` 下创建文件夹，命名格式：`YYYY-MM-DD-{需求名称-kebab-case}`
2. 将需求文档写入为 `需求文档.md`

### A4. 提交

按提交规范提交：

```
docs#: add {需求名称} requirement document [ai][model: mimo-v2.5-pro]
```

### A5. 进入路径 B

需求文档生成后，自动进入路径 B 的流程继续执行。

---

## 路径 B：从需求文档到开发完成

### B1. 阅读需求文档，编写技术方案

仔细阅读需求文档，编写技术方案，使用 Markdown 格式，包含以下章节：

```markdown
# {需求名称} - 技术方案

## 1. 技术选型
<!-- 使用的技术栈、库、框架 -->

## 2. 架构设计
<!-- 整体架构，使用 mermaid 绘制架构图 -->

## 3. 数据结构
<!-- 数据模型、类型定义 -->

## 4. 接口设计
<!-- API 设计、组件接口 -->

## 5. 核心逻辑
<!-- 关键算法、业务逻辑流程，使用 mermaid 绘制流程图 -->

## 6. 文件结构
<!-- 需要新增/修改的文件列表及其职责 -->

## 7. 风险与对策
<!-- 技术风险及应对方案 -->
```

**提交**：

```
docs#: add {需求名称} technical design [ai][model: mimo-v2.5-pro]
```

### B2. 生成开发计划

根据需求文档和技术方案，生成开发计划。**粒度要求：按具体操作级别**，每个子任务应具体到：

- 创建/修改某个文件
- 添加某个函数/方法/组件
- 编写某个测试用例
- 修改某处样式

开发计划格式：

```markdown
# {需求名称} - 开发计划

## 任务清单

- [ ] 1. 创建 `{文件路径}`，定义 {具体内容}
- [ ] 2. 在 `{文件路径}` 中实现 {具体函数/组件名}
- [ ] 3. 在 `{文件路径}` 中添加 {具体方法}
- [ ] 4. 修改 `{文件路径}`，调整 {具体内容}
- [ ] 5. 在 `{文件路径}` 中编写 {测试名称} 测试
...
```

**提交**：

```
docs#: add {需求名称} development plan [ai][model: mimo-v2.5-pro]
```

### B3. Review 开发计划

对开发计划进行全面 Review，生成 Review 报告，包含：

```markdown
# {需求名称} - 开发计划 Review 报告

## 1. 总体评估
<!-- 计划完整性、合理性评价 -->

## 2. 逐项审查

### 任务 1: {描述}
- **评估**：✅ 合理 / ⚠️ 需调整 / ❌ 需重做
- **意见**：...

### 任务 2: {描述}
...

## 3. 发现的问题
| # | 问题 | 严重程度 | 建议 |
|---|------|----------|------|
| 1 | ... | 高/中/低 | ... |

## 4. 遗漏检查
<!-- 是否有遗漏的功能点、边界场景、测试用例 -->

## 5. 建议调整
<!-- 对计划的优化建议 -->
```

**提交**：

```
docs#: add {需求名称} review report [ai][model: mimo-v2.5-pro]
```

### B4. 等待用户确认

**在此暂停**，向用户汇报：

- 已完成：需求文档 / 技术方案 / 开发计划 / Review 报告
- 所有文档位于：`feat/YYYY-MM-DD-{需求名称}/`
- 简要总结 Review 发现的关键问题
- 等待用户确认方案无误，或提出修改意见

**如果用户要求修改**：
- 同步更新所有受影响的文档（需求文档 → 技术方案 → 开发计划 → Review 报告）
- 每次修改后按提交规范重新提交
- 再次暂停等待确认

**如果用户确认无误**（或用户事先说明直接执行到某一步之后自动继续），进入 B5。

### B5. 自动开发阶段

按开发计划逐条实现：

1. 使用 TodoWrite 创建任务列表，跟踪进度
2. 按顺序执行每个子任务
3. **每个子任务完成后**，按提交规范提交：
   - 新增功能：`feat?: {子任务描述} [ai][model: mimo-v2.5-pro]`
   - 修复问题：`fix?: {子任务描述} [ai][model: mimo-v2.5-pro]`
   - 重构代码：`refactor?: {子任务描述} [ai][model: mimo-v2.5-pro]`
   - 样式调整：`style?: {子任务描述} [ai][model: mimo-v2.5-pro]`
   - 其他类型按实际情况选择 scope
4. 更新开发计划中的任务状态（标记为已完成）
5. 所有子任务完成后，向用户汇报开发完成

---

## 文档规范

- 所有文档使用 **Markdown** 格式
- 需要画图时使用 **Mermaid** 语法
- 文档语言与用户输入语言一致（中文输入 → 中文文档）
- 所有文档存放在 `E:\###project\prd\lolachievements\feat\YYYY-MM-DD-{需求名称}\` 目录下
- 文件命名：`需求文档.md`、`技术方案.md`、`开发计划.md`、`Review报告.md`

## 提交规范

遵循全局提交规范：

```
{scope}{test_flag}: {message} [ai][model: mimo-v2.5-pro]
```

| 步骤 | scope | test_flag |
|------|-------|-----------|
| 需求文档 | `docs` | `#` |
| 技术方案 | `docs` | `#` |
| 开发计划 | `docs` | `#` |
| Review 报告 | `docs` | `#` |
| 代码实现 | 按实际（`feat`/`fix`/`refactor`/`style`） | `?` |
