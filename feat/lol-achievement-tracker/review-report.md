## 2. 风险与问题

### 2.1 腾讯接口 CORS 风险（中风险）

**问题**：PRD 中提到"腾讯接口跨域友好"，但实际情况下 `game.gtimg.cn` 可能设置了 CORS 限制。如果浏览器直接 fetch 被拦截，爬取模块将无法工作。

**建议**：
- 开发阶段优先验证该接口的 CORS 头
- 若 CORS 不可用，改为在构建时通过脚本一次性爬取写入 `public/data/heroes.json`，运行时直接读静态文件
- Riot Data Dragon 接口已确认支持 CORS，可作为主要备选

**影响**：T1.2 爬取模块实现方式需调整

### 2.2 localStorage 容量限制（低风险）

**问题**：localStorage 通常限制 5-10MB。170+ 英雄 × N 个成就的记录数据量不大，但仍需考虑极端情况。

**建议**：
- 在导入数据时检查序列化后大小，超过 4MB 时警告用户
- 记录存储结构已设计为稀疏存储（只存有记录的项），无需改动

### 2.3 拼音搜索性能（低风险）

**问题**：`pinyin-pro` 包约 170KB（gzip 后），首次加载有一定体积。170+ 英雄的拼音字段预计算在初始化时完成，性能影响可控。

**建议**：
- 考虑在爬取阶段就将拼音字段写入 heroes.json，避免运行时重复计算
- Fuse.js 的 fuzzy 匹配在 170 条数据上性能无压力

### 2.4 路由与静态部署兼容性（低风险）

**问题**：Vue Router 使用 history 模式时，直接打开 `index.html` 会导致刷新 404。

**建议**：
- Vue Router 使用 `createWebHashHistory()`（hash 模式），兼容纯静态部署
- 或在 Vite 配置中确认 base 路径

### 2.5 成就删除时记录清理的原子性（低风险）

**问题**：删除成就时需同步清理所有英雄的对应记录。当前方案是 achievement store remove action 中调用 record store 的 cleanByAchId。

**建议**：
- 两个 store 操作之间可能存在时序问题（Pinia 是同步的，实际无此风险）
- 可在 record store 中暴露 `cleanByAchId`，由 achievement store 直接调用，确保原子性

## 3. 遗漏项

### 3.1 缺少全局统计页面

PRD 4.3 节要求"全局统计（可选增强）"，包括仪表盘（完成全成就的英雄数、每个成就的完成率、最近完成时间线）。开发计划中未包含此功能。

**建议**：作为 P7 或后续迭代补充，可在 Settings 页中增加统计卡片。

### 3.2 缺少加载态骨架屏的详细设计

P2 任务提到"加载态骨架屏"，但未明确骨架屏的实现方式（CSS animation / 组件）。

**建议**：在 P2 中增加一个 `SkeletonCard.vue` 组件，用 CSS pulse 动画模拟卡片占位。

### 3.3 缺少错误边界的统一处理

爬取失败、导入格式错误、localStorage 异常等场景需要统一的错误处理策略。

**建议**：在 P0 通用组件中增加一个全局错误捕获（Vue `app.config.errorHandler`），统一通过 Toast 展示。

---

## 4. 建议优化

### 4.1 开发阶段可跳过 Riot 备选接口

首次开发时优先实现腾讯接口，Riot 接口作为 fallback 可在 P7 阶段补充，减少初期复杂度。

### 4.2 考虑 hero 数据的版本管理

英雄数据会随游戏版本更新。建议在 heroes.json 中增加 `version` 和 `updatedAt` 字段，方便判断缓存是否过期。

### 4.3 主题方案已完善

主题策略已调整为：默认跟随系统（`prefers-color-scheme`），用户可手动切换（亮色/暗色/跟随系统）。使用 `darkMode: 'class'` + theme store 管理，选择持久化到 localStorage。
